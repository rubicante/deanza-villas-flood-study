# PROVENANCE.md — One-off Artifact Origins

Documents every artifact in `data/raw/` and `data/derived/vectors/` that is NOT
currently regenerated by an automated pipeline or library call. Each entry records
what it is, where it came from, how it was acquired, and whether a reproduction
script is planned (Plan 2).

For pipeline-generated artifacts (in `data/derived/2km_aoi/`), see the relevant
scripts in `scripts/` and their config entries in `config/study.yaml` — those are
reproducible via `python -m scripts`. For library-generated artifacts (in
`data/derived/watershed/` and `data/derived/henderson/`), see `deliverable/` —
those are reproducible via `python -m deliverable._henderson all`.

## Canonical Changes — May 2026 Parcel Correction

Three foundational artifacts were corrected on 2026-05-07. These changes cascade
through all downstream analysis. The old values are recorded here for traceability.

### Parcel Boundary (8.04 ha → 5.06 ha, −37%)

| | Old canonical | New canonical | Root cause |
|---|---|---|---|
| Area | 8.04 ha (MultiPolygon, 3 parts) | 5.06 ha (Polygon) | Old query included Vista Villas |
| Parcels | 67 | 36 | `subname LIKE 'DE ANZA VILLAS%'` matched both communities |
| Vista Villas | Included (31 parcels, APN 14026410xx) | Excluded | Fixed by APN prefix filter |
| Monroe St | Gap between two blocks | Bridged (+6,157 m² ROW) | Road is internal to community, not a boundary |

**Why the old canonical was wrong:** The original SanGIS query used `subname LIKE
'DE ANZA VILLAS%'`, which matched both De Anza Villas (36 parcels) and Vista
Villas (31 parcels, APN prefix 14026410). Both share the subdivision name in the
county assessor database. The California AB1785 legislation (2023) forced
re-acquisition via SANDAG's public FeatureServer (SanGIS removed parcel access
from their REST directory). Re-acquisition surfaced the ambiguous subname match.
AB1785 didn't cause the error — it forced a re-fetch that exposed it.

**New fetch:** `scripts/fetch_parcels.py` → SANDAG Parcels_East FeatureServer
(public, no key). `scripts/correct_parcel.py` filters by APN prefix `14026410`
and bridges the two De Anza blocks with a straight Monroe St connection.

**Known property:** The canonical boundary includes ~6,157 m² of Monroe St ROW
(6.2% of total area). This is asphalt with different hydraulic behavior than the
residential lots. Per-area flood metrics treat the full 5.06 ha as homogeneous.

### FEMA NFHL (40 → 50 features)

| | Old canonical | New canonical |
|---|---|---|
| Features | 40 (38 AO, 1 A, 1 X) | 50 (48 AO, 1 A, 1 X) |
| Query center | Hardcoded Borrego Springs (−116.375, 33.256) | Parcel centroid (−116.401, 33.286) |
| Root cause | Original fetch used arbitrary town-center point | Corrected to parcel-centered spatial filter (8km radius) |

### AOI Buffers — 12–87× Area Correction

This is the largest correction by impact. The old AOI files were committed in the
initial repo commit (2026-05-02) and were never script-generated — no build script
existed before `scripts/build_aois.py` (written 2026-05-07). The filenames contained
"2km" and "8km" but the actual buffers were much smaller.

| | Old file | What it actually was | New file (correct) | Area increase |
|---|---|---|---|---|
| "2km AOI" | 1.17 km², 65-vertex polygon | ~550m buffer (not 2km) | 14.54 km² | **12×** |
| "8km AOI" | 18.68 km², 513-vertex polygon | ~2.4km buffer (not 8km) | 208.56 km² | **11×** |

**Root cause:** The old files were hand-crafted one-offs, committed to the initial
repo with no generation script. The buffer distances encoded in the filenames were
aspirational — the actual geometries were roughly half the stated distance. No
buffer-parameter bug to fix; no unit-conversion error. The files were simply wrong
and the names were misleading.

**Sanity check:** The new `build_aois.py` buffers the parcel in EPSG:5070 (meters)
and was verified against expected area:
- 2km buffer: expected 12.57–14.58 km², actual 14.54 km² ✓
- 8km buffer: expected 201.06–208.97 km², actual 208.56 km² ✓

**Cascade:** Every analysis that used the old 2km AOI — stream extraction, fan
synthesis, HAND, curvature/TPI, DRI roughness comparison, parcel overlay — was
sampling a 12× smaller area than intended. The raw 1m DEM fetched from the old
AOI was 2.0 Mpx (1,412×1,427). The corrected DEM is 20.2 Mpx (4,415×4,567).
All downstream artifacts were regenerated on 2026-05-07 against the correct extent.

**Stream explorer unaffected:** `outputs/maps/stream_explorer.html` loads Henderson
watershed pipeline `.bin` files (`deliverable/_henderson.py`), not 2km AOI outputs.
No regeneration needed.

**Satellite validation deferred:** `scripts/satellite_validation.py` requires
NASA Earthdata Login credentials (.netrc or EARTHDATA_USERNAME/EARTHDATA_PASSWORD).
Neither is configured in this environment. The existing `outputs/maps/satellite_validation.html`
and `outputs/reports/satellite_validation.md` are known-stale (old parcel boundary,
old FEMA). Marked for regeneration when credentials are available.

## data/raw/dem/ — Digital Elevation Models

### deanza_villas_2km_1m_dem.tif
- **What:** 1m DEM covering the De Anza Villas parcel + 2km buffer, in EPSG:5070
  with square 1.000m × 1.000m pixels (1412×1427).
- **Source:** USGS 3DEP via py3dep 0.19.0 WCS (mosaics all available 3DEP
  sources covering the bbox).
- **Acquisition path:** py3dep `get_dem()` → rasterio reproject to 1m² square
  pixels in EPSG:5070 (workaround for py3dep 0.19.0 non-square pixel regression,
  GitHub issue #77).
- **Reproducibility:** Reproducible — `deliverable/fetch.py` implements the
  tile-fetch + reproject + clip pipeline. Also reproducible via the existing
  `scripts/fetch_dem.py`.
- **Notes:** The Eastern San Diego 2017 QL2 lidar tiles (USGS_1m_x55y369,
  x56y369) do NOT cover this parcel (~600m gap). py3dep WCS mosaicking is the
  correct production source. CACHED-INTERMEDIATE PITFALL: if the DEM file
  exists but is corrupt (e.g., all NaN from a failed run), subsequent runs
  will reuse it silently. Verify with `rasterio.open().read(1)[::100,::100]`
  if regeneration is attempted.

### borrego_valley_3dep_10m.tif
- **What:** 10m DEM covering the broader Borrego Valley (wide enough for
  full Henderson Canyon watershed delineation), in EPSG:5070.
- **Source:** USGS 3DEP via py3dep 0.19.0 WCS, resampled to 10m.
- **Acquisition path:** py3dep `get_dem(resolution=10)` → reproject to EPSG:5070.
- **Reproducibility:** Reproducible — `deliverable/fetch.py` with appropriate
  bbox parameters.
- **Notes:** This wide DEM was the key to getting the correct 107 km² watershed.
  The narrow DEM (now removed) produced only 83 km² because it clipped ~5 km of
  western headwater. See `DEVLOG.md` 2026-05-06 ~17:00 UTC.

## data/raw/fema/ — FEMA Flood Hazard Data

### nfhl_borrego_valley.geojson
- **What:** FEMA National Flood Hazard Layer for DFIRM 06073C (Borrego Springs):
  49 features (47 AO, 1 A, 1 X) with depth 1–4 ft and velocity 3–9 ft/sec,
  within 8 km of the De Anza Villas parcel center. CRS: EPSG:4326.
- **Source:** California NFHL Reduced Set on ArcGIS REST:
  `https://services2.arcgis.com/Uq9r85Potqm3MfRV/arcgis/rest/services/S_FLD_HAZ_AR_Reduced_Set_CA_wm/FeatureServer/0`
- **Acquisition:** Reproducible — `scripts/fetch_fema.py` queries the ArcGIS REST
  endpoint with the parcel center, applies 7 validation gates (feature count range,
  required fields, geometry type, total area, zone values, DFIRM_ID consistency,
  ArcGIS error-in-body detection), diffs against canonical, and writes on `--write`.
  Previously one-off; automated 2026-05-07.
- **Reproducibility:** Reproducible — `python scripts/fetch_fema.py --write`.
- **Limitations:** This is the *reduced* set — it excludes Zone D (undetermined
  flood hazard), Zone X minimal hazard, and ancillary layers. A full NFHL state
  download (Option B in `references/fema-nfhl-data-access.md`) requires a manual
  browser download from the FEMA MSC due to TLS cipher-suite restrictions on
  this server.
- **PITFALL — wrong endpoint:** Do NOT use the public
  `services.arcgis.com/2gdL2gxYNFY2TOUb` NFHL endpoint — it has a tiny demo
  extent (East Coast only) that returns zero features for Borrego Springs.

### deanza_villas_complex_boundary.geojson
- **What:** Dissolved boundary of the De Anza Villas condo complex — 67 parcels
  from SanGIS dissolved by `subname LIKE 'DE ANZA VILLAS%'`. CRS: WGS84.
  Properties include `apn`, `parcel_count: 67`, and all 67 APN identifiers.
- **Source:** SanGIS parcel polygon database (San Diego County tax assessor).
- **Acquisition:** **ONE-OFF** — manual query/download from SanGIS, dissolved
  in QGIS or geopandas. Exact acquisition date and method not recorded.
- **Reproducibility:** NOT currently automated. Would require a SanGIS API key

  approximate footprints or buffered points. The dissolved geometry is the

## data/derived/vectors/ — Derived Vector Files

### henderson_watershed_boundary.geojson (WGS84)
### henderson_watershed_boundary_5070.geojson (EPSG:5070)
- **What:** Henderson Canyon watershed boundary — 107.1 km², 1,238,355 cells
  at ~9.3m resolution, 93.5% within Borrego Palm Canyon HUC-12.
- **Source:** WBT `watershed()` on wide 10m DEM with community-bbox pour points,
  polygonized via `rasterio.features.shapes()` → shapely `unary_union` →
  `simplify(10)`, then reprojected to both CRS.
- **Acquisition:** NOW REPRODUCIBLE — `python -m deliverable._henderson watershed`
  calls `deliverable/watershed.py:delineate_watershed()`. Regenerated 2026-05-06.
- **Reproducibility:** Reproducible. Output is geometrically equivalent but not
  byte-identical across reruns (shapely union ordering is floating-point
  non-deterministic).
- **History:** Previously one-off — regenerated from library code in the May 2026
  cleanup pass.

### borrego_palm_canyon_huc12.geojson
- **What:** USGS WBD HUC-12 boundary for Borrego Palm Canyon (181002030302),
  149.1 km². CRS: EPSG:4269 (NAD83 geographic).
- **Source:** USGS Watershed Boundary Dataset, Region 18 (California) shapefile
  from `https://prd-tnm.s3.amazonaws.com/StagedProducts/Hydrography/WBD/HU2/Shape/WBD_18_HU2_Shape.zip`.
- **Acquisition:** **ONE-OFF** — downloaded the full Region 18 WBD shapefile,
  extracted HUC-12 features, filtered to `huc12='181002030302'`, saved as GeoJSON.
- **Reproducibility:** NOT currently automated. Plan 2 task: `scripts/fetch_huc12.py`
  will use the USGS NLDI API for single-HUC retrieval:
  `https://labs.waterdata.usgs.gov/api/nldi/linked-data/huc12pp/USGS-181002030302/basin`
  (returns exactly one polygon, no need to download the full Region 18 shapefile).
- **Notes:** The NLDI basin endpoint is preferred over the S3 download — it's a
  single API call returning only the needed polygon.

### dri_2015_fan_zones.geojson (WGS84)
### dri_2015_fan_zones_epsg5070.geojson (EPSG:5070)
- **What:** Digitized active/inactive alluvial fan zones from DRI 2015
  presentation page 20. Two features: `fan_class=active` and `fan_class=inactive`.
  Confidence: "moderate for broad extents; low-moderate for small polygons."
- **Source:** Color-classified from the 300 dpi page-20 render using RGB
  thresholds tuned for the semi-transparent DRI fills over hillshade
  (pink=active, olive/green=inactive), georeferenced via graticule GCPs
  with linear affine fit. Inset legend masked out before polygonization.
- **Acquisition:** Generated by `scripts/dri_roughness_comparison.py`.
- **Reproducibility:** Reproducible — script is committed. However, the
  classification depends on RGB thresholds tuned to this specific PDF render;
  a different PDF version or renderer could produce different results. This is
  a pragmatic digitization from a map image, not from authoritative source GIS.
- **Notes:** 99.6% of the De Anza parcel falls within the digitized active fan
  zone. No digitized inactive zone overlaps the local 2km roughness raster, so
  the active-vs-inactive roughness comparison from DRI could not be computed
  within the local footprint.
